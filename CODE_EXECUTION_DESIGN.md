# Безопасное выполнение кода в песочнице — проект архитектуры

Документ описывает архитектуру для реализации **реального выполнения кода**
(в отличие от уже существующего режима «Код», который просто маршрутизирует
чат на модель, лучше пишущую код, но ничего не запускает).

## 1. Отличие от существующего режима «Код»

| | Режим «Код» (уже есть) | Выполнение кода (этот документ) |
|---|---|---|
| Что происходит | LLM пишет/объясняет код в тексте | Код реально запускается, возвращается stdout/stderr/exit code |
| Риск | Нулевой — это просто текст | Произвольный код на сервере пользователя — требует изоляции |
| Где живёт | `server/llm.js`, обычный chat-запрос | Новый изолированный сервис-«исполнитель» |

## 2. Цели и границы MVP

**Входит:**
- Кнопка «Запустить» на блоках кода в ответах (рядом с «Копировать»/«Скачать») —
  ручной сценарий.
- **Автономный сценарий для агента:** оркестратор/модель также может вызвать
  выполнение как function-calling инструмент (`run_code`) в рамках диалога —
  например, чтобы проверить свой код перед тем, как показать ответ. Это
  осознанно расширяет поверхность атаки по сравнению с чисто ручным сценарием
  (см. п.3.1 «Дополнительные риски автономного вызова»), поэтому вокруг него
  закладываются отдельные ограничения с самого начала, а не добавляются потом.
- Поддержка популярных языков «из коробки» (Python, JavaScript/Node, Bash, при
  необходимости — что угодно из каталога исполнителя).
- Однократный запуск: stdin (опционально) → stdout/stderr/exit code/время.
- Жёсткие лимиты CPU/памяти/времени/размера вывода.
- Полный сетевой карантин (без доступа в интернет и в домашнюю сеть).

**Не входит в MVP (осознанно откладываем — расширяет поверхность атаки):**
- Многофайловые проекты, установка зависимостей во время выполнения (`pip install`, `npm install`).
- Персистентное состояние между запусками (файловая система стирается после каждого запуска).
- Долгоживущие процессы, серверы, вебхуки, сокеты.
- Multi-tenant квоты на разных пользователей — на первом этапе исходим из
  того, что аккаунт один (админ), но лимиты закладываем сразу.

## 3. Модель угроз

### 3.1 Дополнительные риски автономного вызова (агент как вызывающая сторона)

Когда код запускает не пользователь кликом, а сама модель по собственной
инициативе, добавляются риски, которых нет в чисто ручном сценарии:

- **Prompt injection → код → выполнение без участия человека.** Если модель
  использует веб-поиск или читает внешний контент, вредоносный текст может
  попытаться убедить модель "запусти вот этот код", и без человека в цепочке
  это может произойти автоматически.
- **Использование исполнителя как побочного канала** (side-channel) — модель
  может пытаться использовать `run_code` не для помощи пользователю, а чтобы
  обойти другие ограничения (например, проверить доступность внешнего хоста
  через побочные эффекты, если сетевая изоляция где-то даст течь).
- **Цепочки вызовов** — агент может вызывать `run_code` многократно в одном
  диалоге (например, в цикле "написал → запустил → поправил → запустил снова"),
  что при отсутствии отдельной агентской квоты может быстро исчерпать общий
  лимит запросов пользователя.

Митигации для автономного сценария (в дополнение к общим лимитам из п.6):

- Отдельная, более строгая квота **на инструмент `run_code`, вызванный агентом**,
  чем на ручные клики пользователя (например, не более N автономных запусков
  в рамках одного ответа/диалога).
- Каждый автономный запуск **виден пользователю в интерфейсе** (не скрытый
  побочный вызов) — блок с кодом, который агент выполнил, и его результатом,
  показывается в чате так же, как обычный ответ с блоком кода и кнопкой
  «Запустить», просто инициатором был не клик, а сама модель.
- Учитывая, что режим «Изображение» защищён явным выбором режима именно из-за
  стоимости, а не из-за риска для хоста — здесь риск другого типа (безопасность
  хоста, а не деньги), поэтому автономный доступ можно включить отдельным
  переключателем в настройках («Разрешить модели запускать код автономно»,
  по умолчанию выключено), а не привязывать к выбору режима.

Код полностью недоверенный (пришёл либо от пользователя, либо сгенерирован
LLM) и может пытаться:

1. **Уйти из песочницы** — эксплуатация ядра, container escape.
2. **Съесть ресурсы хоста** — fork bomb, бесконечный цикл, memory bomb → OOM хоста.
3. **Достать данные с хоста/сети** — прочитать файлы вне контейнера, просканировать
   домашнюю сеть, дотянуться до других контейнеров/сервисов на OMV-сервере
   (Keenetic, другие docker-контейнеры пользователя, NAS-шары).
4. **Остаться в системе** — оставить процесс/файл, который переживёт запрос.
5. **DoS сам сервис** — залить очередь тысячами запросов.

Ключевой вывод: **изоляция должна быть на уровне ядра/контейнера**, а не только
на уровне языка (`vm2`/`isolated-vm` защищают только от JS-специфичных атак и
не годятся, если нужны несколько языков).

## 4. Варианты движка исполнения

Собирать с нуля свой Docker-исполнитель — рабочий, но небыстрый путь (нужно
самостоятельно продумать cgroups, seccomp-профиль, очередь, пул контейнеров).
Разумнее взять готовый open-source движок — они уже прошли через это и активно
поддерживаются:

| Критерий | Свой на Docker | [Piston](https://github.com/engineer-man/piston) | [Judge0](https://github.com/judge0/judge0) |
|---|---|---|---|
| Назначение | Полный контроль | Лёгкий stateless-раннер | Полноценный движок (как у онлайн-судей/coding interview) |
| Внешние зависимости | — | Нет | PostgreSQL + Redis |
| Языки «из коробки» | Нужно готовить самому | 40+ | 75+ |
| Холодный старт | Зависит от реализации | 100–300 мс | 200–500 мс |
| Сетевая политика | Настраивается вручную | Default-deny исходящих соединений | Опционально |
| Изоляция | Настраивается вручную | Docker + seccomp-профиль | Docker + cgroups |
| Нужен `privileged`/доп. capabilities | Можно избежать | Да (для seccomp в контейнере) | Да (`privileged: true` у сервиса и workers) |
| Трудозатраты внедрения | Высокие | Низкие (один docker-compose сервис) | Средние (3 компонента + БД) |

**Рекомендация: Piston.** Он самый лёгкий, stateless (не нужна БД), с
default-deny сетью «из коробки» и минимальными зависимостями — оптимален для
домашнего сервера и хорошо ложится на принцип «не тащить лишнюю инфраструктуру».
Judge0 избыточен для одного пользователя (рассчитан на потоковую нагрузку
онлайн-платформ).

**Важная оговорка по обоим движкам:** и Piston, и Judge0 требуют
`privileged`/повышенные capabilities для своего внутреннего механизма изоляции
(seccomp/cgroups настраиваются изнутри контейнера). Это означает, что при
эксплойте ядра теоретический escape ведёт не в обычный контейнер, а в
привилегированный — риск выше, чем у «обычных» сервисов. Компенсируется
это на уровне **топологии сети** (см. п.5), а не отказом от готового решения.

## 5. Рекомендуемая архитектура

```
┌─────────────────────────── Домашний сервер (OMV) ───────────────────────────┐
│                                                                              │
│  ┌────────────────┐        internal docker network         ┌─────────────┐ │
│  │   yadro-app     │  ── HTTP + shared secret, no internet ─▶│   piston    │ │
│  │ (server.js)     │◀──────────── stdout/stderr/exit ────────│ (executor)  │ │
│  └────────────────┘                                          └──────┬──────┘ │
│         │                                                            │       │
│    обычная сеть (Keenetic, интернет, другие контейнеры OMV)          │       │
│                                                                       ▼       │
│                                                    ephemeral privileged-      │
│                                                    контейнер на время запуска,│
│                                                    network: none, uничтожается│
│                                                    сразу после выполнения     │
└──────────────────────────────────────────────────────────────────────────────┘
```

Принципы:

- **Piston — отдельный сервис в отдельной сети** (`code-exec-net`), у которого
  **нет маршрута** ни в интернет, ни в домашнюю сеть, ни к другим контейнерам
  OMV (Portainer/другие стеки). Только `yadro-app` может достучаться до него
  по внутреннему имени.
- **`yadro-app` не получает доступ к Docker-сокету** — только HTTP-клиент к
  Piston. Это ключевая граница: даже если в самом приложении найдут баг
  (например, инъекция), он не даёт прямого доступа к Docker API хоста.
- **Решение по инфраструктуре: отдельный Docker-контейнер на том же хосте**,
  без отдельной ВМ/LXC (проще в развёртывании и обслуживании на вашем OMV).
  Это значит, что весь вес защиты от возможного container escape лежит на
  сетевой изоляции (`code-exec-net`, п.5) и на отсутствии у `yadro-app`
  доступа к Docker-сокету — эти два пункта не опциональны, а обязательны
  именно из-за выбора «без ВМ». Конкретно в `docker-compose.yml`:
  - сервис `piston` без `ports:` наружу — виден только внутри compose-сети;
  - отдельная сеть `code-exec-net` с флагом `internal: true` — Docker не даёт
    ей маршрут во внешний мир; к ней подключены только `yadro-app` и `piston`,
    остальные ваши контейнеры на OMV/Portainer в неё не входят;
  - Docker-сокет хоста (`/var/run/docker.sock`) не монтируется ни в `yadro-app`,
    ни в `piston` напрямую — Piston управляет sandbox-контейнерами через свой
    внутренний механизм (ему для этого нужны повышенные привилегии в своём
    собственном пространстве, но не доступ к хосту извне);
  - если на хосте есть контейнеры с чувствительными данными (шары NAS, базы
    других сервисов) — убедитесь, что у `piston` нет с ними общих сетей и
    общих volume-монтирований.
- **Дополнительный слой защиты — gVisor (`runsc`) как Docker runtime** для
  sandbox-контейнеров Piston: перехватывает системные вызовы в userspace и
  снижает риск эксплойта ядра хоста, не требуя полного доверия к
  привилегированному контейнеру. Настраивается на уровне Docker daemon
  (`--default-runtime=runsc` для соответствующего runtime-профиля). Именно
  при выборе «без отдельной ВМ» эта мера особенно ценна — она компенсирует
  отсутствие лишнего слоя изоляции виртуальной машины. Не блокер MVP, но
  желательно включить до того, как автономный вызов агентом (п.2/п.3.1)
  будет разрешён по умолчанию хотя бы для части пользователей.

## 6. Лимиты ресурсов (конкретные значения для домашнего сервера)

| Параметр | Значение | Почему |
|---|---|---|
| CPU на один запуск | 0.5 vCPU (cgroup limit) | Не даёт одному запросу забрать все ядра |
| Память на один запуск | 128–256 МБ | Достаточно для скриптовых задач, режет memory-bomb |
| Таймаут выполнения | 5–10 сек (compile 10 сек, run 5 сек) | Обрывает бесконечные циклы |
| Лимит процессов (pids) | ≤ 32 | Защита от fork bomb |
| Размер вывода | ≤ 64 КБ, дальше — обрезка с пометкой «вывод обрезан» | Защита от «залить» диск/память логами |
| Сеть в sandbox-контейнере | `none` (Piston: default-deny) | Никакого доступа в интернет/локальную сеть |
| Одновременные запуски | Очередь, максимум 2 параллельно на сервере | Домашнее железо — не рассчитано на параллельную нагрузку |
| Квота на пользователя | Например, 30 запусков/час | Простая защита от случайного/злонамеренного цикла запросов |

Все значения — стартовые, легко подстраиваются в конфиге, если железо
позволяет больше.

## 7. Интеграция с «Ядро»

- Новый модуль `server/codeExec.js`: тонкий HTTP-клиент к Piston
  (`POST http://piston:2000/api/v2/execute`), с маппингом языка блока кода
  (```python → `{language: "python", version: "3.*"}`) и версий через
  `GET /api/v2/runtimes` (кэшировать список при старте).
- Новый эндпоинт `POST /api/code/run { language, code, stdin? }`, защищён
  session-авторизацией, как весь `/api/*`; отдельный rate-limit middleware
  для квоты (п.6).
- **UI (ручный сценарий):** на каждом блоке кода в ответе — кнопка «Запустить»
  рядом с существующими «Копировать»/«Скачать». По клику: спиннер → блок
  результата (stdout зелёным, stderr — красным/оранжевым, exit code, время
  выполнения). Кнопка неактивна для языков вне списка поддерживаемых runtime
  у Piston.
- **Автономный сценарий (агент):** в `server/llm.js` для режимов, где включён
  function-calling, описывается инструмент `run_code({language, code, stdin?})`,
  который под капотом вызывает тот же `codeExec.js`, что и ручная кнопка. Важные
  отличия от ручного вызова:
  - доступно только если в настройках включен переключатель «Разрешить модели
    запускать код автономно» (по умолчанию выключен, см. п.3.1);
  - отдельная, более строгая квота на автономные вызовы в rate-limit
    middleware, отдельная от квоты на ручные клики;
  - результат автономного вызова встраивается в ответ тем же блоком
    «run_code», видимым пользователю, а не скрытым шагом рассуждения.
- Оркестратор (`classifyRoute`) не выбирает режим по наличию кода в тексте —
  доступность инструмента `run_code` регулируется только переключателем выше.
- Каждый запуск (ручной или автономный) логируется в `data/db.json` (или отдельный
  `data/code_runs.log`): время, язык, инициатор (клик/агент), хэш кода (не сам
  код, если не нужно хранить), exit code, длительность — для последующего
  аудита при подозрении на абьюз.

## 8. Чек-лист безопасности перед продакшеном

- [ ] Piston/исполнитель — в отдельной docker-сети без маршрута наружу и
      к другим сервисам OMV.
- [ ] `yadro-app` не имеет доступа к Docker-сокету хоста.
- [ ] Проверены реальные лимиты (запуск fork-bomb/бесконечного цикла/большого
      malloc в тестовой среде — все обрываются лимитами, хост не падает).
- [ ] Rate-limit и квоты включены и проверены, причём отдельно — для ручных кликов
      и отдельно — для автономных вызовов агента.
- [ ] Вывод обрезается по размеру, не приводит к утечке памяти Node-процесса.
- [ ] Переключатель «разрешить автономный запуск агентом» реально блокирует
      вызов инструмента, когда выключен (проверить через попытку прямого
      вызова при выключенной настройке).
- [ ] gVisor (`runsc`) включён для runtime исполнителя до того, как автономный
      вызов агентом будет разрешён хотя бы для одного пользователя.
- [ ] Отдельный `security_subagent_prompt.md`-ревью (по текущей политике проекта)
      именно для этой фичи — она существенно расширяет поверхность атаки по
      сравнению с чатом/генерацией изображений.
- [ ] Если рассматривается публикация на `pplx.app` — обязательно решить, как
      это работает без доступа к вашему домашнему Docker (скорее всего, для
      публичной демо-версии выполнение кода нужно **отключать полностью**,
      оставляя только на локальном/self-hosted инстансе).

## 9. Этапы внедрения

1. Поднять Piston в `docker-compose.yml` рядом с `yadro-app`, в отдельной сети,
   без портов, торчащих наружу (только internal).
2. Реализовать `server/codeExec.js` + эндпоинт, протестировать на мок-движке
   (заглушка вместо реального Piston — как уже делалось для LLM/картинок).
3. Добавить кнопку «Запустить» и блок результата в UI.
4. Прогнать security-ревью по чек-листу из п.8.
5. Только после этого — включать на реальном сервере пользователя с реальным
   Piston (тестировать в этой облачной песочнице без Docker не получится —
   нужен ваш домашний сервер или любая среда с Docker).
