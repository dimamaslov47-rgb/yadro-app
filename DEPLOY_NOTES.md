# Ядро — заметки по деплою

Ядро — личный AI-оркестратор (Perplexity-Max-style интерфейс) на Node.js + Express.
Хранение данных — JSON-файл (lowdb), без нативных модулей — простая сборка Docker-образа
на слабом домашнем сервере.

## (а) docker-compose.yml — точное содержимое

Файл лежит в `/home/user/workspace/yadro-app/docker-compose.yml`. Содержимое:

```yaml
# Стек для Portainer: Stacks -> Add stack -> вставить этот файл -> Deploy.
# Порт 4141 выбран, т.к. на сервере уже заняты 3000 (OpenWebUI), 8000 (Computer/cptr),
# 9000 (Portainer), 8888 (SearXNG).

services:
  yadro:
    # Если разворачиваете стек через "Repository" в Portainer (Git-репозиторий с этим
    # проектом) — можно оставить "build: .", Portainer соберёт образ сам.
    # Если вставляете compose как обычный текст (Web editor, без Git) — сначала
    # соберите образ вручную на сервере: `docker build -t yadro-app:latest .`
    # в каталоге проекта, затем закомментируйте "build: ." и раскомментируйте "image:".
    build: .
    image: yadro-app:latest
    container_name: yadro
    restart: unless-stopped
    ports:
      - "4141:4141"
    environment:
      - PORT=4141
      - DATA_DIR=/app/data
      # SESSION_SECRET можно не указывать: при первом запуске без этой переменной
      # приложение САМО генерирует случайный 64-символьный секрет и сохраняет его в
      # /app/data/.session_secret (внутри volume yadro_data, права доступа 600). При
      # последующих перезапусках контейнера секрет читается из этого файла — сессии
      # пользователей не сбрасываются. Если всё же хотите задать секрет вручную (например,
      # чтобы несколько реплик использовали один и тот же секрет), раскомментируйте строку
      # ниже со своим значением (openssl rand -hex 32) — она имеет приоритет над авто-генерацией.
      # - SESSION_SECRET=замените-на-свой-случайный-ключ
    volumes:
      - yadro_data:/app/data

volumes:
  yadro_data:
```

Рядом лежит `Dockerfile` (образ `node:20-alpine`, без нативной компиляции — только
`npm install --omit=dev`, копирование `server.js` / `server/` / `public/`, `EXPOSE 4141`).

> Начиная с раздела (з) ниже, в `docker-compose.yml` добавлен второй сервис —
> `piston` (исполнитель кода для кнопки «Запустить») — со своей internal-сетью
> `code-exec-net` и volume `piston_data`. Актуальное полное содержимое файла —
> в самом `docker-compose.yml`; здесь оно не дублируется второй раз, чтобы не
> расходиться при будущих правках. Подробности и инструкция по установке
> языковых пакетов — в разделе (з).

## (б) Установка через Portainer

Есть два пути в зависимости от того, как Portainer подключён к репозиторию:

### Вариант 1 — через Git-репозиторий (рекомендуется, самый простой)

1. Залейте папку `yadro-app/` (со всеми файлами: `Dockerfile`, `docker-compose.yml`,
   `server.js`, `server/`, `public/`, `package.json`) в свой Git-репозиторий (GitHub/GitLab/
   свой Gitea и т.п.).
2. В Portainer: **Stacks → Add stack**.
3. Имя стека: `yadro`.
4. Build method: **Repository**.
5. Укажите URL репозитория, ветку, и путь к `docker-compose.yml` (если он не в корне).
6. Нажмите **Deploy the stack** — Portainer склонирует репозиторий и соберёт образ по
   `Dockerfile` автоматически (директива `build: .` в compose это поддерживает).

### Вариант 2 — Web editor (вставить текст compose), без Git

Portainer в режиме **Web editor** не имеет доступа к файлам проекта (Dockerfile и т.д.),
поэтому образ нужно собрать заранее вручную:

1. Скопируйте папку `yadro-app/` на сервер (например, через `scp` или `git clone`, если
   репозиторий всё же есть — просто без интеграции с Portainer).
2. На сервере, в каталоге `yadro-app/`, выполните:
   ```bash
   docker build -t yadro-app:latest .
   ```
3. В `docker-compose.yml` закомментируйте строку `build: .` (или удалите её) — оставьте
   только `image: yadro-app:latest`, чтобы Portainer не пытался пересобрать образ.
4. В Portainer: **Stacks → Add stack**, имя `yadro`, Build method: **Web editor**.
5. Вставьте содержимое `docker-compose.yml` (без строки `build: .`).
6. Нажмите **Deploy the stack**.

В обоих вариантах Portainer создаст именованный volume `yadro_data`, примонтированный в
`/app/data` внутри контейнера — это единственное место, где хранятся все данные приложения
(пользователи, подключения, диалоги). Volume переживает пересоздание контейнера/обновление
образа.

## (в) Первый вход

1. Откройте `http://<адрес-сервера>:4141/` в браузере.
2. Так как пользователей ещё нет, приложение покажет экран **«Создайте admin-аккаунт»**
   (`setup.html`) — введите логин и пароль (минимум 4 символа), нажмите **«Создать аккаунт»**.
   Это единственный момент, когда экран регистрации доступен: как только в базе появится хотя
   бы один пользователь, `/setup.html` перестаёт быть доступным для создания новых
   пользователей (текущая версия поддерживает один аккаунт — расширение до
   мультипользовательской регистрации не входило в объём задачи).
3. После создания аккаунта вы автоматически окажетесь залогинены и попадёте в основной
   интерфейс «Ядро».
4. Дальнейшие входы — через `/login.html` (логин + пароль), сессия хранится в cookie
   `yadro.sid` (30 дней).

## (в.1) Восстановление пароля (без веб-интерфейса)

Если пароль admin-аккаунта забыт, а зайти в интерфейс невозможно, сбросьте его прямо в
контейнере:

```bash
docker exec -it yadro node server/reset-password.js <новый_пароль>
# или так же, через npm-скрипт:
docker exec -it yadro npm run reset-password -- <новый_пароль>
```

Требование к паролю — минимум 4 символа (то же правило, что и в `/setup.html`). Скрипт
напрямую редактирует `data/db.json` (тот же volume `yadro_data`) и хэширует пароль так же,
как это делает сам сервер.

**Важно:** после сброса обязательно перезапустите контейнер —
`docker restart yadro`. Пока сервер работает, он хранит данные пользователя в памяти
процесса, и без перезапуска будет продолжать проверять пароль по старому значению, даже
хотя на диске оно уже изменено.

## (г) Добавление Polza.ai и назначение моделей по режимам

1. В интерфейсе нажмите иконку **шестерёнки** (⚙) внизу сайдбара — откроется окно
   **«Настройки»**.
2. Вкладка **«Подключения»** → **«+ Добавить подключение»**:
   - **Название**: `Polza.ai` (или любое другое, для себя).
   - **Base URL**: `https://polza.ai/api/v1`
   - **API Key**: ваш собственный ключ Polza.ai (`sk-polza-...`).
   - **Модель по умолчанию**: необязательно, можно оставить пустым.
   - Нажмите **«Сохранить»**.
3. Нажмите **«Проверить»** у только что созданного подключения — приложение выполнит
   `GET {base_url}/models` с вашим ключом (`Authorization: Bearer ...`) и покажет список
   доступных моделей или текст реальной ошибки (никогда не показывает фиктивный успех).
4. Перейдите на вкладку **«Модели по режимам»**. Для каждого из режимов —
   **Оркестратор**, **Быстрый**, **Код**, **Сложный** — выберите подключение (например,
   `Polza.ai`) и конкретную модель из выпадающего списка (список моделей подгружается через
   тот же `/models`-запрос).
   - Модель режима **«Быстрый»** используется также как классификатор для **«Оркестратора»**:
     когда пользователь отправляет сообщение в режиме «Оркестратор», сначала выполняется
     короткий запрос к модели «Быстрого» режима с системным промптом «ответь одним словом:
     fast, code или complex», и уже по этому ответу выбирается модель для основного ответа.
     Если режим «Быстрый» не настроен, «Оркестратор» использует режим `fast` напрямую, без
     классификации.
5. Изменения в подключениях и назначениях моделей сохраняются сразу (автосохранение при
   выборе в выпадающем списке), отдельной кнопки «Сохранить всё» не требуется.
6. Пароль можно сменить на вкладке **«Аккаунт»** той же формы настроек.

## (д) Известные ограничения

- **Один администратор.** Экран `/setup.html` создаёт ровно одного пользователя и после
  этого блокируется. Мультипользовательская регистрация/приглашения не реализованы — это
  осознанно вне рамок задачи (личный сервер одного пользователя).
- **SESSION_SECRET теперь генерируется автоматически**, если переданная через окружение переменная
  отсутствует — см. раздел (а) выше. Отдельно генерировать его вручную больше не нужно,
  если у вас только один контейнер с постоянным volume.
- **Счётчик токенов в интерфейсе (в шапке и под каждым ответом) показывается только тогда,
  когда подключённый провайдер реально вернул поле `usage` в ответе (запрос идёт с
  `stream_options.include_usage: true`, как у OpenAI-совместимых API). Не все модели/провайдеры это
  поддерживают — в таком случае счётчик просто не появляется, без выдуманных чисел — это
  нарочное решение, чтобы никогда не врать про расход.
- **Нет HTTPS "из коробки".** Контейнер слушает обычный HTTP на 4141. Если сервер доступен
  из интернета (не только из локальной сети), поставьте перед ним reverse-proxy с TLS
  (например, тот же стек, что использует OpenWebUI/Portainer — Caddy/Traefik/nginx) и cookie
  `secure` в таком случае стоит включить отдельно (сейчас `secure: false`, чтобы работать по
  обычному HTTP в локальной сети).
- **Цитаты (`Источники`) показываются только если модель их реально вернула.** Если
  используемая модель/провайдер не поддерживает поле `citations`/`sources`
  (OpenAI-совместимый или Perplexity Sonar формат), вкладка «Источники» просто не появится —
  это намеренное поведение, чтобы никогда не показывать фиктивные ссылки.
- **Оркестратор — простая эвристика через LLM**, не полноценный router с эмбеддингами:
  классификация — это отдельный короткий чат-запрос к модели «Быстрого» режима с просьбой
  ответить одним словом. При сетевой ошибке или неожиданном ответе классификатора
  автоматически используется fallback на режим `fast`.
- **Тестирование выполнено на моковом LLM-сервере** (`mock-llm-server.js`, порт по умолчанию
  4142), а не на реальном Polza.ai — чтобы не тратить деньги пользователя на автоматические
  тесты. Реальный ключ Polza.ai в тестах не использовался ни разу. Перед боевым
  использованием стоит один раз вручную проверить реальное подключение через кнопку
  «Проверить» в настройках.
- **Толкование "проекты"/"библиотека"/"обзор"** в сайдбаре — это визуальные пункты меню,
  унаследованные от исходного макета `pplx-mockup`; функционально они не реализованы (только
  «Поиск» — то есть чат — работает как настоящий раздел). Расширение этих разделов не
  входило в текущий объём задачи.
- **Свёрнутый сайдбар на мобильных экранах** (`≤ 860px`) полностью скрывается (без
  гамбургер-меню) — так же, как в исходном статическом макете `pplx-mockup`. Это означает,
  что настройки, смена темы и выход недоступны с мобильного экрана уже созданной сессии —
  только через десктопную ширину. Сохранено намеренно, чтобы не менять визуальную структуру
  макета сверх необходимого.
- **Превью-ссылка в этой работе (`/computer/a/...`) не сохраняет cookie сессии** — это
  ограничение самого sandbox-превью (временный инструмент для наглядной проверки), не баг
  приложения: создать admin-аккаунт в превью можно, но сразу после создания сессия может не
  сохраниться и браузер вернётся на экран входа. На реальном сервере (свой домен/IP, без
  sandbox-iframe) cookie сессии работают обычным образом — уже проверено напрямую через
  curl/Playwright на `localhost:4141`.
- **Docker-сборка не проверялась внутри песочницы** (в среде разработки Docker недоступен) —
  `Dockerfile`/`docker-compose.yml` подготовлены по стандартной схеме для `node:20-alpine`
  без нативных зависимостей, но реальную сборку и запуск контейнера стоит один раз проверить
  на целевом сервере пользователя.

## Сквозной тест (для справки)

Полный флоу проверен вручную через Playwright на моковом LLM-сервере: регистрация admin →
логин → добавление тестового подключения → успешная и неуспешная проверка подключения →
назначение моделей по всем 4 режимам → создание диалога → отправка сообщений в режимах
«Оркестратор» (с реальной классификацией и route-badge), «Быстрый», «Код», «Сложный» →
проверка потокового вывода (SSE) → проверка вкладки «Источники» (появляется только при
наличии `citations`, у части ответов её нет — корректно) → удаление диалога → смена пароля →
выход → повторный вход под новым паролем → история диалогов сохранилась. Проверено в светлой
и тёмной темах, на десктопе (1280px) и мобильном (375px).

## (е) Реальный веб-поиск, markdown-ответы и экспорт в файл

- **Кнопка «Веб-поиск»** (бывшая «Компьютер», тот же переключатель) добавляет
  `plugins: [{ id: 'web' }]` к запросу на Polza.ai — работает для любой модели, поддерживающей
  этот плагин (см. https://polza.mintlify.app/gaidy/web-search). Найденные ссылки приходят как
  `choices[0].message.annotations[].url_citation` и показываются во вкладке «Источники» —
  так же, как «родные» citations у Perplexity Sonar-моделей.
- **Ответы рендерятся как markdown** (заголовки, списки, таблицы, ссылки, блоки кода) через
  библиотеки `marked` + `DOMPurify`, вшитые локально в `public/vendor/` — без обращения к CDN
  во время работы приложения.
- **Блоки кода** получают тулбар «Копировать» / «Скачать» — скачивание определяет расширение
  файла по языку из markdown-разметки (```python → `.py`` и т.д.).
- **Кнопка «Скачать» под каждым ответом** открывает меню с тремя форматами:
  - Markdown (.md) — как раньше, чисто на клиенте;
  - Word (.docx) — генерируется на сервере через пакет `docx` (без внешних API, без сохранения
    файла на диске — только в памяти на время запроса);
  - PDF (.pdf) — генерируется через `pdfkit`; шрифт `DejaVu Sans` (файлы в `server/fonts/`,
    добавлены в репозиторий) используется вместо встроенного Helvetica, потому что стандартные
    PDF-шрифты не поддерживают кириллицу — без этого русский текст в PDF превращался бы в набор
    «кракозябр».
  - Оба серверных формата используют очень простой markdown-парсер (заголовки, списки, блоки
    кода, абзацы) — не полноценный markdown-движок; сложная разметка (таблицы, вложенные
    списки) в .docx/.pdf может упрощаться, в .md всегда сохраняется как есть.
- Эндпоинты `/api/export/docx` и `/api/export/pdf` защищены той же сессионной авторизацией,
  что и весь `/api/*`; лимит на размер тела запроса — 2 МБ (общий лимит `express.json`).

## (ж) Генерация изображений (режим «Изображение»)

- Новый режим «Изображение» доступен только по явному выбору пользователя в выпадающем меню
  режимов — оркестратор (`classifyRoute`) никогда не маршрутизирует туда автоматически, чтобы
  не создавать неожиданные расходы на генерацию картинок.
- Backend вызывает `POST /images/generations` у выбранного подключения (для Polza.ai —
  `https://polza.ai/api/v2/images/generations`; путь `/v1` автоматически заменяется на `/v2`,
  так как эта авто-подмена работает только внутри официального SDK, а не при прямых HTTP-запросах —
  см. https://polza.ai/docs/api-reference/images/generations). Список моделей для этого режима
  берётся из общего эндпоинта `/api/connections/:id/test`, без отдельной фильтрации по типу
  «image» (сознательно упрощено).
- Параметры генерации зафиксированы: `n=1` (без выбора количества картинок в UI),
  `size='auto'`, `quality='auto'` (без селектора размера/качества) — минимальный MVP-набор.
- **Стоимость одной генерации** не документирована Polza.ai как фиксированная цена — она
  приходит в ответе как `usage.cost_rub` и просто показывается пользователю под изображением
  (`≈ X ₽`); если провайдер не вернул это поле, стоимость не отображается и не выдумывается.
- **Хранение изображений:** сгенерированные картинки сохраняются как base64 (`b64Json`)
  непосредственно в `data/db.json` — это заметно увеличивает размер файла базы данных, но это
  осознанный выбор: CDN-ссылки (`url`), которые Polza.ai возвращает как альтернативу, живут
  только 7 дней согласно документации провайдера, и после этого срока изображение в истории
  диалога стало бы недоступным.
- Если провайдер не успевает сгенерировать изображение синхронно (до 120 секунд) и возвращает
  асинхронный статус `pending`/`processing`, backend не опрашивает `/v1/media/{id}` — это
  осознанно не реализовано в MVP, пользователь увидит понятную ошибку вместо зависшего запроса.
- На фронтенде во время ожидания показывается индикатор загрузки со спиннером; после получения
  ответа блок с изображением поддерживает: превью, скачивание файла (декодирование base64 →
  Blob, без внешних сервисов), подпись с `revisedPrompt` (если провайдер скорректировал запрос)
  и строку с названием подключения/модели и стоимостью. Переключатель «Веб-поиск» скрывается в
  этом режиме, так как он не имеет смысла для генерации изображений.
- Проверено вручную через Playwright на моковом сервере: назначение подключения и модели для
  режима «Изображение» в настройках → отправка запроса → индикатор загрузки → корректный рендер
  готового изображения с сохранением естественных пропорций (без искажения) → повторное открытие
  сохранённого диалога показывает изображение из истории тем же образом.

## (з) Выполнение кода — кнопка «Запустить» и переключатель автономного запуска

Полная архитектура и модель угроз — `CODE_EXECUTION_DESIGN.md`. Ниже — только итог того, что
реально реализовано в коде, и границы MVP.

**Сканирование:**

- Где угодно в ответе (в любом режиме) модель может вернуть блок кода с распознаваемым
  языком (python/javascript/bash и алиасы: python3/py, node/nodejs/js, sh/shell/zsh) —
  рядом с «Копировать»/«Скачать» появляется кнопка «▶ Запустить».
- Клик → спиннер → POST `/api/code/run` → под блоком кода появляется результат:
  stdout, stderr (если есть), exit code и время выполнения, с зелёным/красным оформлением
  в зависимости от exit code. Кнопка показывается только если язык блока входит в
  список поддерживаемых языков, который бэкенд забирает у исполнителя при старте
  (`GET /api/code/languages`); если исполнитель недоступен, список пуст, кнопки нет ни у одного блока.
- **Лимиты:** таймаут выполнения 5 с (компиляция — 10 с), вывод обрезается по 64 КБ,
  лимит кода на входе 200 КБ, квота **30 запусков/час на пользователя** (сбрасывается при
  рестарте сервера — самый простой MVP-вариант, без персистентного стора лимита). При превышении
  квоты — ответ 429 с понятным сообщением.
- **Журнал:** каждый запуск через кнопку логируется в `data/db.json` в коллекции `codeRuns`
  (id, userId, `initiator: 'manual'`, язык, хэш кода (без самого кода — только sha256),
  exit code, длительность, время).

**Настройка «Выполнение кода» (новая вкладка в модалке настроек):**

- Тумблер «Разрешить модели запускать код самостоятельно» сохраняется в `data/db.json`
  (`settings.allowAutoCodeExec`, по умолчанию `false`) и корректно восстанавливается при
  повторном открытии настроек. **Обновление:** автономный вызов теперь реализован через
  function calling — см. раздел «Function calling и run_code как инструмент агента» ниже.

**Локальная разработка (`mock-piston-server.js`):**

- Для разработки/тестов без Docker в корне проекта лежит `mock-piston-server.js` —
  минимальный HTTP-сервер, повторяющий формат API Piston (`/api/v2/runtimes`,
  `/api/v2/execute`) и реально выполняющий код через `python3`/`node`/`bash` на самом
  сервере (НЕ изолировано, только для быстрой локальной проверки). Адрес задаётся
  переменной `PISTON_URL` (в docker-compose — `http://piston:2000`, локально —
  `http://127.0.0.1:4143` по умолчанию).

**Docker-compose — сервис `piston`:**

- Образ `ghcr.io/engineer-man/piston`, без проброса `ports:` наружу, волюм `piston_data`
  для кэша языковых пакетов, собственная internal-сеть `code-exec-net` (только
  контейнер `yadro` видит `piston` по имени, никакого выхода в интернет/LAN у самого Piston).
- **Важная оговорка:** внутри `internal: true`-сети у Piston нет доступа в интернет,
  а значит он не сможет скачать языковые пакеты (python/node/bash и т.п.) сам по себе.
  Поэтому первый запуск — двухфазный: (1) временно разрешить интернет (закомментировать
  `internal: true`), установить языки через `cli ppman install python node bash` внутри
  контейнера, (2) вернуть `internal: true` обратно и перезапустить — описано
  шаг за шагом в комментариях над сервисом `piston` в самом `docker-compose.yml`.
- Контейнер `yadro` подключён одновременно к `default` и `code-exec-net`, получает
  переменную `PISTON_URL=http://piston:2000`.

**Проверено вручную (curl + Playwright на моковом Piston-сервере):**

- `GET /api/code/languages`, `GET`/`POST /api/settings`, `POST /api/code/run` (успех с exit 0,
  ненулевой exit code, таймаут, неподдерживаемый язык, пустой ввод) — через curl.
- В интерфейсе (режим «Код»): отправка запроса → появление кнопки «▶ Запустить»
  только на поддерживаемом языке → клик → корректный результат с зелёным «✓ Выполнено» для exit 0 и красным «✗ Завершилось с ошибкой» + traceback для
  исключения → настройка «Выполнение кода»: тумблер переключается и
  корректно восстанавливается после перезагрузки страницы.
- **Не проверено** (вне сегмента): реальный Docker/Piston на боевом сервере —
  в sandbox-среде Docker недоступен, весь код протестирован только против мокового
  сервера.

## з) Function calling, память профиля и планировщик задач

**Function calling и `run_code` как инструмент агента:**

- `server/tools.js` экспортирует `RUN_CODE_TOOL` — JSON-схему функции `run_code`
  (`language`, `code`, `stdin`) в формате, который понимают большинство
  OpenAI-совместимых провайдеров (поле `tools` в запросе `chat/completions`).
- `server/llm.js`: `chatCompletionWithTools()` — один нестримовый запрос с полем
  `tools`; `runToolLoop()` — цикл до `maxRounds` раундов: если модель вернула
  `tool_calls`, каждый выполняется через переданный executor, результат
  добавляется в историю как `role: 'tool'`, и запрос повторяется, пока модель не
  ответит обычным текстом или раунды не закончатся.
- В `/api/chat/send` цикл включается **только** если `settings.allowAutoCodeExec === true`
  и режим сообщения не `'image'`. Регистрируется единственный инструмент — `run_code`.
  Каждый вызов транслируется клиенту через SSE-событие `tool_event`
  (`{status: 'pending'|'ok'|'err', tool, args, ...}`) — фронтенд рисует инлайн-заметку
  над финальным ответом («🔧 Агент выполняет инструмент «Код»…» → ✅/❌).
- `executeToolCall('run_code', args, {userId})` в `server.js` делит **тот же** rate-limit
  (`CODE_RUN_LIMIT`/час) и журнал `codeRuns`, что и ручная кнопка «Запустить» —
  различаются только полем `initiator: 'agent'` vs `'manual'`.
- **Почему не добавлен поиск как инструмент:** в проекте нет собственного
  поискового backend'а — сегодня веб-поиск делегируется целиком провайдеру через
  `plugins: [{id: 'web'}]` в самом запросе (см. режим «Веб-поиск» в интерфейсе), а не
  вызывается моделью как отдельный tool. Добавление `web_search` как function-calling
  инструмента потребовало бы либо своего поискового API, либо моста к тому же
  провайдерскому плагину — оставлено вне этого сегмента.
- **Лимит:** максимум 3 раунда вызова инструментов на одно сообщение
  (`maxRounds: 3`) — защита от бесконечного цикла модели.
- **Ограничение:** промежуточные раунды (`assistant` с `tool_calls` и `tool`-ответы)
  не сохраняются в истории треда — только в журнале `codeRuns` и в `tool_event`
  для текущего запроса. При следующем сообщении в том же треде модель не «помнит»
  промежуточные шаги предыдущего вызова инструмента, только финальный текстовый ответ.
- **Тест без реальных ключей провайдера:** `mock-llm-server.js` симулирует
  `tool_calls`, когда в запросе есть `tools` с `run_code` и последнее сообщение
  пользователя матчит `/запусти|выполни|посчитай|run.?code|execute/i` — первый раунд
  возвращает вызов инструмента, второй (с `role: 'tool'` в истории) — обычный ответ.

**Память — профиль пользователя:**

- `GET/PUT /api/profile` читают/пишут `profileNote` (строка, лимит 4000 символов) у
  текущего пользователя в `data/db.json`.
- В `/api/chat/send` заметка (если не пустая) подкладывается как **первое**
  system-сообщение перед историей треда: `Память о пользователе (учитывай при
  ответе...): <profileNote>`.
- **Важно — это НЕ полноценная долгосрочная память:** нет автоматического
  запоминания фактов из диалога, нет векторного поиска/эмбеддингов, нет выборки
  релевантных фрагментов — один плоский текстовый файл, который пользователь
  редактирует вручную и который целиком попадает в промпт каждого запроса.
  Подходит только для короткой заметки («работаю с PowerShell», «отвечай кратко»),
  не для хранения истории или больших объёмов контекста — иначе будет раздувать
  каждый запрос токенами.
- Фронтенд: вкладка «Память» в настройках — textarea + кнопка «Сохранить».

**Планировщик периодических задач:**

- `server/scheduler.js`: `startScheduler({db, getConnection, chatCompletionOnce})` —
  простой `setInterval` (тик каждые 60 секунд) без внешней cron-библиотеки. На каждом
  тике проверяет все `enabled` задачи, у которых `nextRunAt` в прошлом, и запускает их.
- **Интервалы, а не cron-синтаксис:** задача настраивается как «каждые N минут»
  (`intervalMinutes`), минимум — `MIN_INTERVAL_MINUTES = 5` (защита от спама запросами
  к провайдеру). Нет поддержки cron-выражений («каждый день в 9:00», «по будням») —
  это отдельное расширение на будущее.
- При срабатывании задачи выполняется один запрос `chatCompletionOnce` с промптом
  задачи через выбранный режим/модель (`maxTokens: 2000`), результат добавляется как
  новое сообщение в тред, который автосоздаётся при первом запуске задачи и
  переиспользуется дальше — название треда `⏱ <task.title>`.
- **Нет отдельного канала уведомлений:** результат появляется только как сообщение в
  этом треде — нет push/email/Telegram уведомления о завершении. Пользователь узнает
  о результате, только открыв тред (или через список «Недавние» в сайдбаре).
- API: `GET/POST /api/scheduled-tasks`, `PATCH/DELETE /api/scheduled-tasks/:id`,
  `POST /api/scheduled-tasks/:id/run-now` (немедленный запуск вручную, для проверки
  задачи не дожидаясь интервала).
- Фронтенд: вкладка «Планировщик» — карточки задач (тумблер включения, «Запустить
  сейчас», удаление, отображение последней ошибки) + форма создания.

**Проверено (curl + Playwright, мок-провайдер, без реальных ключей):**

- Профиль: `GET`/`PUT /api/profile`, сохранение и восстановление заметки.
- Планировщик: полный CRUD, валидация интервала (< 5 минут отклоняется), запуск
  задачи с ненастроенным режимом (корректная ошибка в карточке) и с настроенным
  режимом (успешное выполнение, создание треда).
- Function calling: включение тумблера → отправка сообщения-триггера в режиме
  «Код» → SSE `tool_event` (pending → ok) → инлайн-заметка в интерфейсе →
  финальный ответ модели → запись в `codeRuns` с `initiator: 'agent'`.
- Визуально (Playwright, светлая и тёмная тема): вкладки «Память» и «Планировщик»
  в настройках, форма создания задачи, карточка с ошибкой (для интервала выше)
  чтения, тумблер компактного размера в карточках, заметка `tool_event` в чате.
- **Не проверено** (вне сегмента): реальный провайдер (AITunnel/Polza.ai) с
  function calling — формат `tool_calls` может отличаться между провайдерами,
  нужна проверка на реальном ключе перед продакшн-использованием этой функции.

## Режим «Компьютер», вложения в чат, сборка файлов задачи

**Режим «Компьютер» (полноценный агент-оркестратор):**

- Новый режим `computer` добавлен в список `MODES` наравне с `orchestrator`/`fast`/
  `code`/`complex`/`image`. Настраивается моделью так же, как остальные режимы —
  вкладка «Модели по режимам», плюс отдельная кнопка «Компьютер» в сайдбаре
  (`navComputerBtn`), которая сразу открывает новый диалог в этом режиме.
- **Инструменты включены всегда**, без тумблера «Автозапуск кода»: в этом режиме
  модели доступны `run_code` (тот же исполнитель через Piston, что и в обычном
  function calling) и новый `write_file` (сохраняет текстовый файл в рабочую
  область задачи). `maxRounds = 8` (против `3` по умолчанию для обычного
  function calling) — агенту даётся больше шагов на сложную задачу.
- **`write_file(filename, content)`** — `server/tools.js` (JSON-схема для
  function calling) + `server/files.js` (`writeTaskFile`): сохраняет файл в
  `DATA_DIR/task-files/<threadId>/`, санитизирует имя файла, лимиты
  `MAX_FILE_BYTES = 2 МБ` на файл и `MAX_TOTAL_BYTES = 20 МБ` суммарно на тред
  (превышение — понятная русская ошибка, которую видит модель как результат
  tool-вызова и может отреагировать).
- **Сборка в один архив:** как только в треде появляется хотя бы один файл,
  ответ ассистента получает `taskFiles`/`taskFilesUrl`, в чате рендерится карточка
  «📦 Скачать итоговый файл (N файлов)», а по `GET /api/threads/:id/files.zip`
  отдаётся ZIP со всеми файлами треда (архивирует `archiver`, в памяти, без
  временных файлов на диске). Именно эту зip-ссылку получает пользователь —
  отдельного скачивания по одному файлу не предусмотрено.
- Route на скачивание отдаёт `Content-Disposition` с ASCII-фолбэком имени файла
  и RFC 5987 `filename*=UTF-8''...` — заголовки HTTP не допускают кириллицу
  напрямую в `filename=`, поэтому название треда (часто на русском) кодируется
  отдельно для браузеров, которые понимают `filename*`.
- Файлы треда **живут до удаления диалога**: `DELETE /api/threads/:id` вызывает
  `clearTaskFiles` и стирает папку `task-files/<threadId>/` целиком. Нет отдельной
  кнопки «очистить файлы» без удаления треда.
- **Исключён из планировщика** — как и режим `image`, `computer` нельзя выбрать
  при создании/редактировании периодической задачи (`400 invalid_input`). Логика:
  агент, который пишет файлы без присмотра и без возможности их скачать в момент
  завершения, не имеет смысла в автоматическом расписании.
- **Важное ограничение:** `write_file` — это отдельный инструмент от `run_code`.
  Файлы, которые код *создаёт сам* при выполнении в песочнице (`run_code`), **не**
  попадают автоматически в архив задачи — Piston возвращает только stdout/stderr,
  а не файлы, оставленные на диске исполнителя. Чтобы файл попал в скачиваемый
  архив, модель должна явно вызвать `write_file` с его содержимым.

**Вложения в чат — изображения и документы:**

- Кнопка со скрепкой (`attachBtn`/`attachBtnFollowup`) рядом с полем ввода,
  drag-and-drop на всю область композера (подсветка рамки при наведении файла) и
  вставка из буфера обмена (`paste` на текстовое поле) — три равнозначных способа
  прикрепить файл. Лимит — `MAX_ATTACHMENTS_CLIENT = 5` на клиенте (дублирует
  серверный `MAX_ATTACHMENTS = 5`) файлов за одну отправку.
- **Изображения обрабатываются полностью на клиенте**: `FileReader` кодирует файл
  в base64 `dataUrl` прямо в браузере, на сервер уходит только в составе запроса
  `/api/chat/send` — отдельного эндпоинта загрузки изображений нет. Лимит размера
  — `MAX_IMAGE_DATA_URL_CHARS = 9 МБ` (проверяется на сервере в `sanitizeAttachments`).
- **Документы (PDF/DOCX/TXT/MD)** идут через `POST /api/uploads/extract` —
  `multer` (память, без сохранения на диск) → `server/attachments.js`
  (`pdf-parse` для PDF, `mammoth.extractRawText` для DOCX, обычное чтение UTF-8
  для TXT/MD) → извлечённый текст с лимитом `MAX_EXTRACTED_CHARS = 12000` символов
  возвращается клиенту и хранится только в памяти вкладки браузера до отправки.
- На сервере `buildOutgoingContent()` вставляет текст документа как размеченный
  блок `[Приложенный документ «имя»] ... [/Приложенный документ]` в текст сообщения
  всегда (не зависит от наличия изображений); если есть хотя бы одно изображение —
  всё сообщение превращается в OpenAI-формат `content: [{type:'text',...},
  {type:'image_url',...}]` для vision-моделей. Без вложений формат сообщения не
  меняется (обычная строка) — это осознанно сохранено, чтобы не задеть провайдеров/
  тестовые моки, ожидающие строковый `content`.
- В базе (`db.json`) у сообщения пользователя сохраняются только метаданные
  вложений (`{type, name}`) — ни `dataUrl`, ни извлечённый текст документа не
  попадают на постоянное хранение, чтобы не разрасталась база и не хранились
  потенциально чувствительные файлы дольше одного запроса.
- **Важное ограничение:** содержимое вложения (картинка или текст документа)
  передаётся модели только в том сообщении, где оно было прикреплено. При
  следующих сообщениях в том же треде оно не повторяется — иначе стоимость
  токенов росла бы с каждым ответом. Если нужно, чтобы модель «помнила» файл в
  продолжении диалога, стоит переслать его или пересказать содержимое текстом.
- Лимит тела запроса увеличен `express.json({ limit: '15mb' })` (было `2mb`) —
  запас нужен из-за base64-изображений (объём кодирования на ~33% больше
  исходного файла) при нескольких вложениях в одном сообщении.

**Проверено в этом сегменте (curl + Playwright, мок-провайдер и мок LLM-сервер,
без реальных ключей AITunnel/Polza.ai):**

- `POST /api/uploads/extract` — извлечение текста из `.txt` (кириллица, две
  строки) через реальный запрос multipart/form-data.
- Режим «Компьютер» целиком: отправка сообщения → мок-LLM отвечает вызовом
  `write_file` → SSE `tool_event` (call → result) → файл сохранён на диске →
  `taskFiles`/`taskFilesUrl` на сообщении ассистента → SSE `files_ready` →
  `GET /api/threads/:id/files.zip` отдаёт корректный ZIP с ожидаемым содержимым.
- `DELETE /api/threads/:id` — подтверждено, что папка `task-files/<threadId>/`
  физически удаляется вместе с тредом.
- Валидация планировщика — создание задачи с `mode:'computer'` отклоняется
  (`400 invalid_input`), как и `image`.
- Вложение-изображение в обычном (не «Компьютер») режиме — сообщение с
  `content` в виде OpenAI vision-массива успешно обработано мок-сервером
  (после доработки мока — вытаскивает текстовую часть из массива для своей
  тестовой логики) и обычные сообщения без вложений (строковый `content`)
  продолжают работать без изменений — регрессии не найдено.
- Вложение-документ — текст документа корректно вставлен в исходящее
  сообщение как размеченный блок, метаданные вложения (без текста) сохранены
  в истории сообщения.
- Playwright (светлая/тёмная тема не проверялась отдельно для этой функции,
  использована тёмная — тема по умолчанию в тестовом профиле): кнопка
  «Компьютер» в сайдбаре и переключение режима, кнопка-скрепка открывает
  системный выбор файла, drag&drop подсвечивает рамку композера при наведении
  файла и снимает подсветку при уходе, вставка изображения из буфера обмена
  создаёт чип вложения, чип корректно удаляется по кнопке ×, карточка
  «Скачать итоговый файл» появляется в чате и содержит верную ссылку на ZIP.

**Найдено и исправлено в этом сегменте:**

- `public/script.js` использовал `MAX_ATTACHMENTS_CLIENT` в проверке лимита
  вложений, но константа была не объявлена — при попытке прикрепить файл
  вложение падало с `ReferenceError` в консоли браузера и чип не появлялся.
  Добавлено объявление `const MAX_ATTACHMENTS_CLIENT = 5` рядом с `MODE_LABELS`.
- Индикатор результата `tool_event` в чате проверял только `exitCode === 0`
  (формат результата `run_code`), поэтому успешный результат `write_file`
  (JSON без поля `exitCode`) всегда отображался как «❌ завершился с ошибкой»,
  хотя файл сохранялся корректно. Проверка переписана: сначала ищет
  `exitCode` (для `run_code`), затем `ok` (для `write_file`), иначе — по
  тексту результата (сообщения об ошибке начинаются с «Ошибка»).
- `archiver@8.0.0` (последняя версия на момент установки) — полностью новый
  ESM-only API без функции-фабрики `archiver('zip', opts)`, на которую
  рассчитан код в `server/files.js`. Из-за этого сборка ZIP всегда падала с
  `archiver is not a function`. Зафиксирована версия `archiver@^7` (последняя
  с привычным CommonJS API) в `package.json`.

**Не проверено (вне сегмента):**

- Реальный провайдер (AITunnel/Polza.ai) с multimodal-контентом и `write_file`
  через настоящий vision-инструментированный ключ — формат `tool_calls` и
  структура `content`-массива могут отличаться у разных провайдеров, нужна
  проверка перед продакшн-использованием.
- Настоящий PDF/DOCX файл через `pdf-parse`/`mammoth` (тестировался только
  `.txt`) — стоит проверить на реальном документе перед релизом.

## Расширение форматов документов, вложений и транскрибация (новый сегмент)

**Новые npm-зависимости** (без нативных биндингов — подтверждено
`find node_modules -name "*.node"` — пусто): `exceljs`, `pptxgenjs`,
`adm-zip`. Используются существующие: `archiver@^7` (не `^8`, см. выше),
`docx@^9`, `pdfkit@^0.20`, `mammoth@^1.12`, `pdf-parse@^2.4`, `multer@^2.3`.

### Автономная генерация документов (`create_document`)

В режиме «Компьютер» модели доступен новый инструмент `create_document`
(наравне с `run_code` и `write_file`) — модель сама решает вызвать его,
без участия пользователя. Поддерживаемые форматы: `pdf`, `docx`, `xlsx`,
`pptx`, `csv`, `rtf`, `odt`. Параметры: `filename`, `title`, `content`
(текст/markdown-подобная разметка — для pdf/docx/rtf/odt), `rows`
(массив массивов — для xlsx/csv), `sheets` (мультилист xlsx), `slides`
(массив `{title, bullets, notes}` — для pptx). Результат — файл сразу
пишется в `data/task-files/<threadId>/`, попадает в `taskFiles` сообщения
и доступен через уже существующий `GET /api/threads/:id/files.zip`.

- `.doc` и `.xls` **сознательно не поддерживаются** для генерации (нет в
  списке форматов инструмента) — легаси-форматы требуют тяжёлых библиотек,
  решено не добавлять.
- Сквозной тест пройден через реальный HTTP-запрос (не только на уровне
  функций): сообщение в режиме «Компьютер» → мок-LLM вызывает
  `create_document` с форматом `xlsx` → файл физически создан → ZIP с
  сообщения скачан и открыт `ExcelJS` — данные (заголовок, кириллица, число)
  совпадают. Остальные форматы (`pdf`, `docx`, `pptx`, `csv`, `rtf`, `odt`)
  проверены на уровне прямого вызова функций-генераторов
  (`server/documents.js`) — валидный ZIP/бинарник, корректная кириллица.

### Расширенное чтение вложений (`/api/uploads/extract`)

Помимо ранее поддержанных `.txt`/`.pdf`/`.docx`/изображений, теперь читаются:
`.rtf` (собственный парсер с корректной вырезкой служебных групп
`fonttbl`/`colortbl`/`stylesheet` и любых `{\*...}`-групп по спецификации
RTF, декодирование кириллицы `\'XX` через `windows-1251`), `.odt` (текст из
`content.xml` внутри ZIP), `.xlsx` (через ExcelJS, лист → текст с
табуляцией), `.pptx` (текст всех текстовых блоков по слайдам), `.csv`,
`.json`, а также широкий список текстовых кодовых расширений (`.py`, `.js`,
`.ts`, `.go`, `.rs`, `.sql`, `.html`, `.css`, `.ini` и др. — читаются как
обычный текст).

- `.doc` и `.xls` при попытке приложить возвращают понятную ошибку на
  русском («Старый формат .doc не поддерживается — пересохраните как
  .docx») вместо падения с невнятной ошибкой парсера — проверено реальным
  HTTP-запросом.
- Лимит извлекаемого текста не изменился: `MAX_EXTRACTED_CHARS = 12000`.
- Проверено реальными HTTP-запросами (`multipart/form-data`) для `.rtf` и
  `.csv` — оба вернули корректно извлечённый текст с кириллицей.

### Транскрибация аудио/видео (`/api/uploads/transcribe`)

Новый эндпоинт `POST /api/uploads/transcribe` (форма как у
`/api/uploads/extract`: `multipart/form-data`, поле `file` + `mode`).
Поддерживаемые расширения на фронтенде: `.mp3`, `.wav`, `.mp4`, `.m4a`,
`.webm`, `.ogg`. Сервер отправляет файл на `{baseUrl}/audio/transcriptions`
подключённого провайдера (Whisper-совместимый эндпоинт), модель
захардкожена как `whisper-1`. Провайдер для запроса берётся из назначения
режима «Компьютер» (`modeAssignments.computer`), с запасным вариантом —
`complex`.

- **Важное ограничение:** транскрибация зависит от того, поддерживает ли
  подключённый провайдер (AITunnel/Polza.ai) Whisper-совместимый эндпоинт
  `/audio/transcriptions`. Если провайдер такой эндпоинт не отдаёт —
  вернётся ошибка провайдера как есть; собственного fallback-распознавания
  речи в приложении нет.
- Результат оформлен в том же формате, что и `/api/uploads/extract`
  (`{filename, text, truncated}`), поэтому фронтенд переиспользует весь
  существующий код обработки вложений-документов без изменений — файл
  просто вставляется в исходящее сообщение как текстовый блок с
  расшифровкой.
- Проверено реальным HTTP-запросом против мок-эндпоинта
  `/audio/transcriptions` (мок не разбирает реальное аудио, просто отдаёт
  фиктивный текст) — файл дошёл, ответ получен и обработан по тому же пути,
  что и обычные текстовые вложения.

**Не проверено (вне сегмента, требует реального ключа провайдера):**

- Реальный вызов `/audio/transcriptions` у AITunnel/Polza.ai — формат
  ответа, лимиты размера файла и поддерживаемые кодеки нужно уточнить по
  документации конкретного провайдера перед продакшн-использованием.
- Крупные `.pptx`/`.xlsx`-вложения (десятки слайдов/листов) — извлечение
  текста проверено на компактных тестовых файлах, лимит `MAX_EXTRACTED_CHARS`
  обрежет вывод для больших документов, как и для остальных форматов.

## Мультимодельный оркестратор режима «Компьютер» (новый сегмент)

Режим «Компьютер» больше не обязан работать на одной жёстко назначенной
модели. В Настройки → «Модели по режимам» для строки «Компьютер» появился
пункт «— авто (агент сам подбирает) —»: при выборе подключения без
конкретной модели (`modeAssignments.computer = {connectionId, model: null}`)
агент сам решает, какая модель (или несколько моделей) нужна под конкретную
задачу, на основе списка моделей выбранного подключения. Ручное закрепление
одной модели за режимом «Компьютер» (как раньше) остаётся доступным и
работает как прежде — оркестратор просто не включается, используется
старый прямой путь.

### Автоопределение возможностей моделей (`server/modelCapabilities.js`)

`inferCapabilities(modelId)` — эвристика по регулярным выражениям на имени
модели, без обращения к провайдеру за метаданными (у большинства
OpenAI-совместимых API таких метаданных просто нет):

- `audio` — `whisper`, `transcri`
- `image_gen` — `dall-e`, `stable-diffusion`, `flux`, `imagen` и т.п.
- `code` — `coder`, `code-`, `codestral` и т.п.
- `vision` — `gpt-4o`, `claude-3`, `gemini`, `qwen-vl` и т.п.
- `reasoning` — `opus`, `gpt-4`, `gpt-5`, `sonnet`, `70b`, `large`, `ultra`,
  `max` и т.п.
- `fast` — `mini`, `haiku`, `flash`, `nano`, `small`, `turbo` и т.п.
- по умолчанию — `general`

Пользователь может **вручную поправить** авто-разметку любой модели через
новую панель в Настройки → «Модели по режимам» (появляется, когда для
режима «Компьютер» выбрано подключение): список моделей подключения с
чекбоксами возможностей. Снятие всех чекбоксов возвращает модель к
авто-разметке. Хранится в `db.json` как
`modelCapabilityOverrides.<connectionId>.<modelId>: [tags]`; переопределение
для конкретного подключения не затрагивает те же ID моделей у другого
подключения. API: `GET /api/computer/model-pool` (текущий пул с
авто+переопределёнными тегами), `PUT /api/computer/model-pool`
(`{modelId, capabilities:[...]}`, пустой массив — сброс к авто).

### Планировщик → подзадачи → сборка → проверка (`server/orchestrator.js`)

Для каждого сообщения в режиме «Компьютер» без закреплённой модели:

1. **Планирование.** Модель с тегом `reasoning` (если такой в пуле есть,
   иначе первая доступная) получает список моделей пула (с их тегами
   возможностей, максимум 30 в промпте — иначе промпт планировщика
   становится непомерно длинным при большом количестве моделей у
   провайдера) и просят вернуть строгий JSON: список подзадач (до 5,
   агрессивное разбиение — по одной подзадаче на каждую самостоятельную
   часть запроса), нужен ли итоговый файл и в каком формате. При ошибке
   разбора JSON — запасной путь: одна подзадача на весь запрос целиком
   (то есть с текущим провайдером/сообщением поведение не хуже старого
   однмодельного режима).
2. **Подзадачи.** Каждая подзадача выполняется параллельно
   (`Promise.all`) на модели, подобранной под её `capability` из пула;
   у подзадачи свой цикл вызова инструментов (до 4 раундов) и итоговое
   краткое резюме для передачи на сборку.
3. **Сборка.** Если подзадача была одна и она успешна — сборка
   пропускается (её результат сразу становится финальным ответом:
   экономия одного лишнего вызова модели). Если подзадач несколько или
   единственная подзадача завершилась с ошибкой — отдельный вызов
   собирает результаты всех подзадач в единый ответ, сам может вызывать
   инструменты (включая `create_document` — например создание Excel-файла
   со сведёнными данными из нескольких подзадач).
4. **Проверка.** Отдельный вызов (техническая + смысловая проверка,
   как запрошено) возвращает вердикт `{ok, issues}`. Если `ok:false` —
   выполняется **один** повторный цикл сборки с учётом найденных проблем
   и повторная проверка; результат отдаётся пользователю в любом случае
   (даже если вторая проверка снова `ok:false`) — оркестратор не блокирует
   ответ, чтобы задача не зависала без результата из-за несовершенства
   мок- или реальной модели-контролёра. Ремонтный цикл ограничен одним
   повтором намеренно — компромисс между качеством и стоимостью.

### Новые события потока (SSE) для интерфейса

`planning_start {model}`, `plan {subtasks, outputFormat, source}`,
`subtask_start {id, title, model, capability}`,
`subtask_done {id, title, model, ok, summary|error}`,
`assembly_start {model}`, `verify {ok, issues, repaired}` — фронтенд
рисует их живой карточкой прогресса над ответом (план подзадач с
назначенными моделями, статус выполнения каждой, отметка сборки и
результат проверки). Событие `route` в режиме «Компьютер» теперь
приходит дважды: сначала без модели (пока идёт планирование), затем с
финальной моделью, которая реально формировала ответ пользователю
(последняя модель сборки либо модель единственной успешной подзадачи).
Существующие режимы эти события не отправляют — карточка на них не
появляется, изменение аддитивное.

### Стоимость и задержка — важная оговорка

Агрессивное разбиение + отдельный вызов планировщика + краткое резюме на
каждую подзадачу + сборка + проверка (+ до одного ремонтного цикла) —
это заметно больше вызовов модели на одну задачу, чем раньше (когда
режим «Компьютер» просто отправлял сообщение одной закреплённой модели).
Для простых задач (одна подзадача, есть однозначно подходящая модель)
оркестратор всё же схлопывается до 3 вызовов (план → подзадача →
проверка, без отдельной сборки) — это тот же порядок, что и раньше плюс
проверка. Для сложных многосоставных задач по нескольким моделям и
форматам вывода расход кредитов и времени ответа растёт пропорционально
числу подзадач. Это осознанный выбор пользователя (агрессивность
разбиения — «максимально агрессивно», глубина проверки — «техническая +
смысловая»); при необходимости снизить расход — можно вернуться к ручному
закреплению одной модели за режимом «Компьютер» в любой момент.

### Что проверено в этом сегменте (мок-провайдер)

- Быстрый путь (одна подзадача, без сборки): корректный выбор
  возможности/модели, выполнение инструмента, проверка `ok:true`,
  финальный ответ с метаданными `orchestration` в сообщении.
- Разбиение на несколько подзадач (изображение → `vision`, код → `code`)
  с параллельным выполнением, сборка с вызовом `create_document`
  (сгенерированный `.xlsx` подтверждён скачиванием и открытием —
  корректные заголовки и строка данных), проверка `ok:true`.
- Ремонтный цикл: первая проверка `ok:false` → повторная сборка
  (`assembly_start` срабатывает второй раз) → повторная проверка
  (`repaired:true`) → ответ всё равно доставлен пользователю, несмотря на
  то что и вторая проверка вернула `ok:false` (намеренное поведение —
  не блокировать выдачу результата).

**Не проверено (требует реального ключа провайдера с несколькими
моделями разных возможностей):** качество автоопределения возможностей и
самого разбиения/сборки/проверки на реальных ответах LLM, а не мок-текстах
— поведение зависит от того, насколько точно реальная модель-планировщик
следует запрошенному строгому JSON-формату промпта.
